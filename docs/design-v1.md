# EntryLib portal — v1 design (draft)

Status: working draft · Date: 2026-11-09 · Companion to `platform/requirements.md`, the claimset specification (v0.39), the lab record specification (v0.20) and the revision specification (v0.6)

This document fixes what the first version of the portal does, how it is built and what it leaves for later versions. Requirements are cited by their `PLT-` IDs.

## 1. Versions

| Version | Scope |
|---|---|
| **v1** | Classification (OpenAlex subfield and topics), submission of claimset packages, guarantor consent, publication, browsing and search for LLMs (HTTP API and MCP server), safe-ingest screening, rate limits and spam controls, a one-page human home page |
| v2 | AI reviews, scores, revisions (revision spec), human-facing pages |
| v3 | DOIs, entity resolution |
| v4 | Search by frame and atom |
| v5 | Claim graph, contradiction detection |

v1 keeps room for v2: versions, the review folder of the registry and the review fields of responses exist from the start, empty.

Planned work, for the portal and for the claimset package, is tracked in GitHub issues labelled `roadmap` (entrylib/portal and entrylib/claimset), not in this document.

## 2. Principles

1. **LLM first.** v1 serves agents. Humans get one page explaining what EntryLib is and how to point an agent at it.
2. **Publication on consent.** A valid package whose guarantors confirm is published. Quality is judged by the v2 reviewer, not by a gate.
3. **Nothing is withdrawn.** Published versions stay. Problems are marked with notices (§9). The only exception is legal removal.
4. **The registry is the record; the database is an index.** Every published document is committed to a public git registry. The portal's database can be rebuilt from it. A rebuild (`portal reindex`, and the one when the app starts, §7.1) first brings the portal's clone to the registry's `main` on GitHub (github mode), and does nothing if it cannot, so the index is never rebuilt from a copy behind the record; and it replaces the index in one transaction, so a rebuild that fails leaves the index as it was.
5. **No dependence on one host.** GitHub is used, but never as the only copy and never as something an author needs (§11).
6. **Open.** Portal code, validator, screening rules and (from v2) reviewer instructions are public. The converter stays private.
7. **The format moves on its own.** The claimset package (format rules, validator, lab record) changes often. The portal and the registry work with whatever claimset they are given, at least a minimum version and with no upper bound, so a claimset release needs no change to either. On the server, the app installs the newest claimset release from PyPI each time it starts (`deploy/start.sh`), so updating claimset is a restart, not a rebuild. The registry's check installs the current portal and the newest claimset on each run. The portal's CI runs daily against the newest claimset, so a claimset change the portal cannot work with is seen the same day. Each version's `validation.json` records the validator that checked it.

## 3. Architecture

```
agent ──zip──▶ API (FastAPI) ──▶ validator + deterministic screening ──▶ pending (Postgres, 48 h)
                                                │
guarantor ──ORCID sign-in──▶ consent page ──────┘
                                                ▼
                         bot opens PR on registry ──▶ CI: validator, lab chain, screening
                                                ▼ (green)
                         merge + tag ──▶ static files (JSON, MD) + search index + archive requests
                                                ▼
                    readers: static files · /api/search · /mcp · /llms.txt
```

- **App:** Python, FastAPI. One process serving the submission API, consent pages, search API and MCP server. It calls the `claimset` package for validation, rendering, verifiability and patches; it never reimplements the spec.
- **Database:** PostgreSQL with pgvector. Pending submissions, consents, the search index (full text and embeddings), and each published version's file as `jsonb`.
- **Static files:** every published file and its rendered views, generated at publication and served directly by Caddy. Most read traffic touches no application code.
- **Packaged files:** kept with their claimset, at `/p/<key>/v<n>/files/<path in the package>`, so that a claimset's files live in its folder and leave with it; a file unchanged from the version before is a hard link, not a copy. Images are shown on the pages from there; other files are downloads. Files stored by checksum before November 2026 (`/files/<sha256>`, still the `uri` in those versions) were moved to `/p/<key>/v<n>/files/<artefact id>.<ext>`, and their old addresses redirect there (`legacy_files`). Object storage (DigitalOcean Spaces) may take the folder's place later.
- **Classifier:** a separate service running OpenAlex's open topic model (§5.4).
- **Embeddings:** a small open embedding model run on the server's CPU.

## 4. Submission

### 4.1 Package

A submission is the **package** of claimset spec §2.5: a BagIt bag (RFC 8493), as a zip or a folder, built by `claimset package`:

```
bagit.txt
manifest-sha256.txt
data/
  paper.claimset.json
  files/fig3.png
  files/results-per-series.csv
```

- A packaged artefact has a `uri` relative to `data/` and `version` `sha256:<checksum>` (rule 70). At publication the platform replaces the relative `uri` with the file's permanent location. A claimset with no files may be submitted as the JSON file alone. A claimset submitted alone names no packaged file: an artefact whose `uri` is a relative path is refused under rule 70 (claimset spec v0.41 §2.5, amended 2026-11-11), since the file would not arrive and the paper would be published without it. The refusal says how to send the package.
- Limits (rule 77, spec v0.35): at most 200 files, 50 MB a file, 200 MB in all; safe paths only; the manifest lists exactly the payload; an allowlist of file types (gzipped data files accepted; archives, executables and links refused). The validator checks a zip before unpacking it. Artefacts are served as downloads, never rendered (SVG included).

### 4.2 Flow

1. The package or the claimset file reaches the portal by one of the routes of §4.4. No account and no token. `POST /api/validate` runs the same checks and keeps nothing; `POST /api/score` gives the scores the file would have once published, as the MCP tool `score` does, and keeps nothing (added 20 November 2026, the maintainer: "That could help agents that don't have python": an agent with neither a terminal nor MCP can score over plain HTTP). Uploads over 210 MB are refused.
2. Synchronous checks: package limits (rule 77), validator (claimset §10, current spec version only), deterministic screening (§6), and for a new claimset the duplicate check (§4.5). Errors are returned in machine-readable form and nothing is kept.
3. A valid package becomes a pending submission with an internal ID (PLT-21) and a **consent link** for each human guarantor. The agent passes the link to its human.
4. The guarantor opens the consent link (or, without it, signs in with ORCID at `/submissions`, Your submissions, linked from the Submit page, the menu and every page's footer, which lists every pending submission naming their iD, each with a one-time ticket valid for 30 minutes and bound to that iD, behind its Confirm button and its Cancel button) and sees a preview of the claimset's page as it will be published: the paper page itself (`site.preview_page`, the same header, sections, panel and Score as a published page, made by the same page view, which escapes every value the file gives), with no identifier, citation, version list or claim pages of its own yet. Like a published paper it opens on the *paper view* (§7.4; decided 19 November 2026, the maintainer: the preview showed only the record, which is not what a reader sees first), and its *Paper · Record* switch leads to the record at `/consent/<token>?view=record` and back, both on the consent page with the bar and what confirming means; in the paper view a link to what only the record holds (evidence, an artefact) leads to the preview's record, as a published paper's leads to `/p/<id>/record`. A bar at the top, kept in view while they read, says it is a preview and not published yet, and holds the Confirm button (or, for a submission waiting for its package, the way to attach it first); above the paper, what confirming means. Your submissions shows each submission waiting for the person signed in as a person reads a paper (decided 20 November 2026, the maintainer: "instead of showing principal claims etc, show there the summary, the list of claims (their names) and general information about the claimset - something that a human would read"): its title, its authors, subfield, licence, the number of claims and references and how long it waits, then its summary, then its claims by ID and name (a claim without a name by the first sentence of its statement), each principal claim marked; then *Open the preview* and *Confirm and publish*, side by side on one line. The preview is the consent page's, at `/submissions/<submission>/preview` (and `?view=record`), opened with the sign-in session by a guarantor the submission names who has not confirmed; its bar leads back to Your submissions, where the Confirm button is, since the session only lists and previews. The reading view is no longer on the list: the preview shows the paper, and the agent has the text. Its sections come in the order a guarantor acts on them: *Waiting for you*, *In progress*, *Published*, *Closed in the last 14 days*, with a menu of them beside the page, as a specification's contents are (a bar that opens it on a phone), each with how many it holds (decided 23 November 2026, the maintainer: "Published needs to move before Closed in the last 14 days and we need to have a short menu ... to scroll fast ... improve the Published view to have a bit of useful information"). Each published paper shows its title, its identifier and version, when it was published and when it was last updated, its Support score, how many claims it holds and how many are principal, its status when it is retracted, withdrawn or under an expression of concern, and links to its paper view, its record and its text for AI; there is room in the row for an action on the paper. What these pages show of a pending file (the file with the platform's verifiability, which takes a full validation, and the preview's scores) is made once per file and kept until its window ends (`previews.py`, keyed by the file's checksum and the installed claimset and rubric; decided 20 November 2026, when each visit took 7.5 s for a simulation study). Read takes each paper's scores from the score file written with its pages, not from the rubric on the first visit after a start. They sign in with ORCID (the `/authenticate` scope of ORCID's free public API: the portal learns only their iD and name) and so confirm (PLT-15, PLT-16). The iD must be the guarantor's; anyone else is refused and the submission stays pending. Each sign-in is tied to its consent link by a single-use OAuth state that lasts 30 minutes. After any ORCID sign-in on EntryLib (a consent link, Your submissions, the removal form), the portal keeps a sign-in session for 8 hours (a random token in an HTTP-only, Secure, SameSite=Lax cookie; only its hash is stored, with the iD and name, table `signin_sessions`): Your submissions then opens the list at once, with new tickets on each visit, until the session ends or the person signs out (`POST /signout`). The session only lists and previews; confirming still takes a ticket from the list or the ORCID sign-in of a consent link.
   - Limits are applied here (§8): at most 2 new claimsets confirmed per guarantor in seven days, and 3 new versions of one claimset in a day. A confirmation over the limit is refused, and the submission stays pending until its window ends.
   - A correction is submitted by the guarantor of the current version: the API refuses one naming anyone else.
5. All guarantors must confirm within **48 hours**. Otherwise the submission is deleted and never shown. A guarantor who no longer wants a submission cancels it at `/submissions` (or from the consent link): it is refused at once ("cancelled by its guarantor"), its content deleted as on expiry, and it stops counting against the limits.
   - **Your submissions** (`/submissions`): after the same ORCID sign-in, a guarantor sees what waits for them (to confirm or cancel), what waits for another guarantor or is being published, what closed in the last 14 days (cancelled, refused, expired, with the reason) and every claimset they guarantee. Not public, not indexed. The page is laid out as the paper view (§7.4): one column of text, and to its right the contents every page has (*On this page*, *Top*, each section with its count; on a phone, the bar at the top), with its sections always open. In the contents, *Waiting for you* and *Published* open, as the paper view's sections do, the list of their papers by name, each a link to it; the arrow beside them leads to the section.
6. On consent, the platform classifies the claimset, assigns the provisional ID, version, date and status, computes verifiability (PLT-14, PLT-22), and opens a pull request on the registry (§5.3); the submission is `publishing`. A publication worker does this at once and again on a ten-minute loop, so a confirmation is never lost to a restart or an unavailable classifier or GitHub; one worker runs at a time (a database lock). The identifier is kept on the submission, so a retried round reuses it. One version of a claimset is in flight at a time: a second correction waits until the first is published. In local mode (development) the worker commits to a local registry clone instead.
7. The registry's checks run on the PR (§6). If they pass, the portal squash-merges it and tags the merge commit; publication follows (§5.3). If they fail, the PR is closed with the reasons as a comment, its branch is deleted, and the submission is `refused` with the reasons. The ID is not reused.
8. `GET /api/submissions/{id}` reports the state at every step (`pending`, `confirmed`, `publishing` with the link to its registry pull request, `published`, `refused`, `expired`) and which guarantors have confirmed, never the content. The ID is unguessable; consent links are shown only in the response to the submission, and only their hashes are stored. While pending, the state gives `confirm_url`, the `/submissions` page, for a guarantor without the link. `/confirm`, its old address, redirects there. Closed submissions are forgotten 14 days after their window ends.

A claimset has exactly one guarantor: the main author, the person to contact, a person with an ORCID iD, who submits it (claimset spec v0.36). So a submission has one consent link; the validator refuses a second guarantor and organisations in any position but conversion guarantor. The API takes native claimsets only: converted claimsets are published by the conversion service, whose conversion guarantor (a person or an organisation) answers for them.

Corrections (PLT-23) go through the same flow, with `paper.id` naming the existing claimset (§4.5). Revisions with responses wait for v2.

### 4.3 From the lab to EntryLib

No GitHub account is needed at any point. An author working with claimset-lab:

```
claimset lab export -o claimset.json                 # exists
claimset package <paper>.claimset.json -o <paper>.zip  # exists: the BagIt package
claimset submit <paper>.zip                          # new: posts the package, prints the consent link
claimset status <submission id>                      # new
```

The MCP server offers the same as `validate`, `submit` and `submission_status` tools, for agents without a terminal. The `claimset-submit` skill is updated to end with these steps.

### 4.4 Submission routes

Every route ends in the same checks and the same pending submission (§4.2); they differ only in how the file arrives.

| Use case | Route | What is sent |
|---|---|---|
| A full pipeline in a terminal (claimset-lab, `claimset package`) | `POST /api/submissions`, the zip as the request body (`claimset submit`) | The package, with its files |
| Evidence already deposited elsewhere (Zenodo, GitHub, an institutional repository) | `POST /api/submissions` with the JSON as the body, or the MCP tool `submit` | The claimset JSON alone; its artefacts' `uri` are the deposits' https URLs and are left there: the portal neither downloads nor copies them. An artefact with a relative `uri` names a file of a package, and the JSON alone is refused |
| A claimset with no files | as above | The claimset JSON alone |
| A person with a file, no terminal | `/submit`, a page with a file picker | The zip or the JSON, sent as the request body of `POST /api/submissions` by the page's script |
| An agent that reaches EntryLib only through MCP but can send a request from where the package is (a code tool, a shell without `claimset`) | The MCP tool `upload_url`, then a `PUT` of the zip to the address it gives, then `validate`, `score` or `submit` with `upload_id` | The package itself, straight to the portal: its bytes never pass through the model. The address is single-use, expires after 2 hours and takes at most 210 MB |
| An agent with no way to send a file (a chat with only the MCP connector) | The MCP tool `submit` with the claimset and `package_with_consent: true` (or `POST /api/submissions?package_with_consent=true`) | The claimset JSON now; the package with the guarantor's consent: the consent page asks for the zip the agent produced, checks that it holds the claimset submitted, and confirming waits until it does (§4.2 step 4) |
| A claimset with a few text files, from an agent with no way to send a file | The MCP tools `validate`, `score` and `submit` with `claimset` and `files` | The claimset JSON with the text of the files its artefacts name (`{path, text}`); the portal builds the package from them with the claimset package's `build_from`, and checks it as an upload. A file whose checksum differs from the `version` its artefact records is refused. At most 10 MB in all, and in practice what the model can write out: every character passes through its output |
| An agent that cannot upload a large file (MCP, a chat) but can deposit it | `POST /api/submissions/from-url` with `{"url": …}`, or the MCP tool `submit` with `package_url` | An https URL of the package or the JSON, which the portal fetches |

- **By URL.** The portal fetches https URLs only, from public addresses only (loopback, private, link-local and other non-global addresses are refused, checked on the address actually connected to), follows at most 5 redirects (each checked again), and stops at 210 MB or 120 seconds. What it fetches is checked exactly as an upload is.
- **The upload page** is static HTML and one script, served by the app with a Content-Security-Policy that allows only that script. It shows the response's submission ID, consent link and errors as text; nothing submitted is rendered.
- **The MCP server** carries what the model writes, never a file: MCP has no way to attach one, so whatever an agent sends through a tool passes through the model's output. A package therefore reaches the portal outside the tool call: sent by the agent to an upload address (`upload_url`), or attached by the guarantor on the consent page (`package_with_consent`). The claimset JSON, and a few text files (`files`, at most 10 MB in all), may be sent in the call. Binary content is never sent in a tool call, base64 included: a model copying random characters is slow, costly and error-prone.
- **Upload addresses.** `upload_url` (MCP) returns `{upload_id, url, method: PUT, expires, max_bytes}`. The address holds a secret, is used once, expires after 2 hours, and takes at most 210 MB; what is sent there is checked only when a tool uses it, and is deleted on expiry or once submitted. Issuing and sending count against the `upload` limit (§8).
- **The package with consent.** A submission sent with `package_with_consent` whose artefacts name files by relative path is held as pending and **waiting for its package**: everything else is checked as usual, rule 70 for the claimset alone excepted. The consent page (and Your submissions) asks for the zip and lists the files it must hold; the portal checks it as a package and that its claimset is the one submitted (equal, the artefacts' `version` checksums of packaged files aside, which `claimset package` writes), then stores it in place of the JSON. Confirming is refused until it is attached. The status says `waiting_for: package`.
- Batch submission, many claimsets confirmed by one sign-in, is future work (portal issue #34).

### 4.5 New versions and duplicates

- **New versions.** The identifier says which claimset a new version belongs to; ORCID proves the person may change it. A new version sets `paper.id` to the claimset's identifier, given in the response that published it and in every search result; the submission is then a correction of that claimset, and its guarantor must be the guarantor of the current version, who confirms with ORCID as for a new claimset. The portal never guesses a claimset from its title or its author. Handing a claimset over to a new guarantor is future work (portal issue #35). A new version is made from the current version, and the portal checks it (decided 21 November 2026, portal issue #179, after a correction prepared from version 2 was published over version 3 and removed the summaries and sections version 3 had added): one that names the version it was made from (`paper.based_on`, claimset spec v0.44 as amended on 2026-11-21; `claimset correct` writes it) is refused (409) unless that is the current version, and the message names the current version. Whatever it names, the patch from the current version (the package's `raw_patch`) is read for what it removes: the response to the submission (`removals`, `removals_note`), the consent page and Your submissions list the removed fields by kind with the objects they are removed from ("summary: C1, C2, …", "paper.sections", whole objects), so that the guarantor sees what they confirm; for a new version that does not name its origin, they say that removals may be the undoing of a later version.
- **Duplicates.** A new claimset (no `paper.id`) whose guarantor already guarantees a claimset with the same title (compared in lower case with punctuation and spacing removed), published or confirmed and being published, is refused (PLT-19, in part), naming the existing identifier or submission: a new version of it sets `paper.id`. A submission still waiting for consent does not count, so a fixed file can be submitted again before confirming and the first one expires; the check runs again when the guarantor confirms, so two of them are not both published. A genuinely different paper with the same title is submitted with `new_paper=true` (a query parameter of the API, an argument of the MCP tool).

- **Papers converted by their authors.** A claimset that restates a published paper (`paper.published_as`, or before it a `manuscript` artefact, with a DOI; claimset spec §3.6) names that paper once on EntryLib: a second claimset with the same DOI is refused (409), whatever its title or guarantor; a new version sets `paper.id`. The portal asks Crossref, then DataCite, for the paper's authors (`source.py`, after `crossref.py`'s settings): the guarantor's ORCID iD among them confirms authorship; their family name, when the record gives no ORCID iD to compare, is accepted; a guarantor who is neither is refused (403) when the record lists ORCID iDs, and otherwise accepted with "not confirmed" recorded. The contributors list the paper's authors first, in the order of the record's byline, then anyone else, agents last (claimset spec §3.11, Order): each author is matched to the one contributor with their ORCID iD or, without one to compare, their family name, and a claimset that lists the matched authors in another order, or anyone before or between them, is refused (422), naming the byline's order; an author matched to no contributor or to several is left out of the comparison and named in the report. The message of `/convert` asks for this order. An unknown DOI or an unreachable registry does not block a submission; the report says it was not checked. The consent page shows the paper, the authorship found and the co-authors' ORCID iDs the record gives and the claimset lacks.

### 4.6 A LaTeX draft of a published paper

A guarantor can turn a claimset they published into the draft of a paper for people, to finish and post as a preprint (decided 23 November 2026, the maintainer: "It needs to run on the portal so that there is a motivation for people to submit"). It is free; preparing a paper for a particular journal is a later paid service, as are the others listed in the maintainer's *EntryLib paid services*.

- **Which papers.** Research that has no paper yet: a claimset made with claimset-lab or written directly as a claimset. Not a claimset that restates a published paper (`published_as`, a `manuscript` with a DOI, or `converted`): it has its paper (`latex.refusal`; decided 23 November 2026, the maintainer: "We should refuse to build for the claimsets converted from the existing/published papers ... And make sure that user understands this", then "Add the button to those who wrote claimset directly"). Your submissions says so: such a paper says why in its row ("No LaTeX draft: it restates a published paper", the full reason on hover), the rule is said once above the papers, and the draft's address gives the full reason (403).
- **Where.** Each such paper of *Published* on Your submissions has a *LaTeX draft* button, for its current version. It opens `/submissions/draft/<key>`, a confirmation page (the sign-in session, a guarantor of that paper) that says what the draft is and is not; its *Build the draft* button (`POST`, the same address) builds the draft and sends it as a zip. Nothing is built before that, and nothing built is kept. No sign-off: a confirmation, then the file. Building counts against the limit of validation and scoring (§8). A retracted or withdrawn paper has no draft.
- **Made by code, not a model.** `latex.py` writes the draft from the published file alone, in Python, the same every time: what the claimset holds is set out as a paper, and nothing is added. What a paper needs and the claimset does not hold (an introduction's motivation, a discussion, a conclusion, acknowledgements, a missing affiliation or declaration) is a visible gap, `\gap{…}`, printed in the PDF as a red note, and listed with its line in `GAPS.md`.
- **What it holds: a paper and its supplement** (revised 23 November 2026, the maintainer: the first draft was "a unusable claimset in latex"; make it "look more like a paper with gaps"). The draft is laid out as a paper, not as the claimset's objects: no ID of the record (a claim, evidence, hypothesis, run, limitation or artefact) stands in the paper's prose; `traceability.csv` keeps the link from each line to the object it comes from, and the supplement keeps the record. *The paper* (`paper.tex`, a plain `article`): the title; the human authors with their affiliations and ORCID iDs (agents are not authors; the models are named in the statement on the use of AI); the summary as the abstract and the keywords; an introduction that motivates and holds no claim (revised 23 November 2026, the maintainer: "Make sure that the Introduction does not have claims - it's role is in motivating the research"): the gap for the motivation, with the contributions (`paper.contributions`, by name and `summary`) listed under it in `GAPS.md`, a roadmap of the sections, the claimset's citation, and *Earlier work*, a literature review: its gap, then one paragraph per work the claims relate to, the relations' notes about it (each once) and its citation, never which claim extends it ("Proposition 16 extends B25"), which `GAPS.md` lists under the gap; a work related without a note is listed there only; then the paper's sections (`paper.sections`, else one *Results*), each opening with a gap for a sentence that leads into it. In a section each claim is set out by what it is: a formal claim (`type: formal`, or proved) is a theorem (principal), proposition (secondary) or lemma (supporting), numbered by LaTeX with one counter, its name as the theorem's title ("Theorem 3 (Asymmetry lies in (−1, 1))"; no name, no title), its proof after it when short (at most 6 steps and 600 characters) and in the appendix otherwise, each step's `by` as a reference ("by Definition 2", "by Theorem 1"); any other claim is a paragraph with its name as a run-in heading when its section holds more than one such claim, its statement as text, the tables and figures it cites as Table n and Figure n. A definition stands just before the claim that first uses it (as in the paper view), a definition with a formula of a concept, method, model or variable as a numbered `definition`, others as a run-in paragraph under their term; an assumption as a numbered `assumption` before the first claim that rests on it; the design of an evidence object as a run-in paragraph, *Design*, before the first claim that cites it, without the lab record's words for its runs and plan. Evidence that only checks a proved claim by computation (simulation evidence of a formal claim) is not in the sections: the appendix says once what the checks were and what they found. Then the discussion: its gap, the limitations as a paragraph (a deviation from a plan is the record's, in the supplement), the open questions; the conclusion's gap; declarations (funding, competing interests, ethics, consent); author contributions (CRediT, with a gap asking the author to check them when one person is named); the use of AI; data, materials and provenance; references; the appendix: the longer proofs, then the numerical checks. A table of more than 40 rows prints the rows the claims cite, and its CSV file holds them all; a table whose rows are held in a file is named once, by its address. Figures are `figures/figure-<n>` in the order they appear, and no caption begins with an ID. *The supplement* (`supplement.tex`): the claimset as a record, for the reader who checks: each claim by its ID with its number in the paper, its statement, everything that supports it (the steps of its proof with their foundation, the results it cites with their values, its tables), its assumptions, limitations and relations; every evidence object; every limitation with the claims it affects; every artefact. Layouts for other kinds of research (empirical, qualitative, review, argument) are not yet chosen from what the claimset holds (issue #201): such claims are set out as paragraphs, as above.
- **Files.** `paper.tex`, `supplement.tex`, `references.bib`, each evidence table as `tables/<evidence>.<table>.csv`, the figures as `figures/figure-<n>`, `traceability.csv` (each line of `paper.tex` and `supplement.tex` that comes from the claimset, with its file and the object and field it comes from), `GAPS.md` and `README.md` (how to compile them, and what to keep). No PDF: the author compiles it.
- **The link to EntryLib.** The draft names its claimset in three places, each of which the author is asked to keep: a footnote on the title ("This paper is the human edition of the claimset entrylib:2026.000001@v2, https://entrylib.org/p/2026.000001/v2"); the claimset cited in the introduction, as an entry of `references.bib`; and the statement on data, materials and provenance, which links the record, the lab record and the artefacts. The citation is the part that lasts: a journal's template keeps it where it drops a footnote. A double-blind journal will ask for all three to be removed for review.
- **Mathematics.** A formula of the file is set as mathematics only when every command it uses is one the portal's MathML reader knows (`mathml.py`) and it holds nothing TeX would read as something else (`%`, `^^`, `$`, `#`); otherwise it is written as text, verbatim. So no file can make the draft run a command.
- **References.** Written from what the portal knows: a DOI's metadata from Crossref as kept at publication (`doi_metadata`; never asked for at this point), a claimset published here, an arXiv identifier, a URL, the reference as printed. Whether every reference can be resolved is checked when a claimset is submitted, not here.

## 5. Registry and lab records

### 5.1 Registry

`entrylib/registry` holds the published record in the layout of revision spec §2.4. A claimset's folder is `<year>/<block>/<name>/` (revision spec v0.6): the block is the number divided by 1000, so no folder holds more than a thousand entries, and the name is the identifier with `doi:` removed and `:` and `/` replaced by `_`. `entrylib:2026.000001` is in `2026/000/entrylib_2026.000001/`; the path follows from the identifier alone. Files per version: `claimset.json`, `lab.jsonl` (when a lab record is packaged) and `validation.json` (the submission's warnings, the validator and the classifier that were used). Only the EntryLib GitHub App writes to it, through pull requests: one squash commit per version (`Publish entrylib:2026.000001@v1`), tagged `<name>-v<n>` (`entrylib_2026.000001-v1`). The main branch is protected: no force-pushes or deletion, and changes only through pull requests whose `check` passes. The repository's own files (README, licence notice, workflow) change through maintenance pull requests, which the same check tells apart from publications.

The registry holds the record documents only: claimset files, lab records, validation reports, and from v2 reviews, responses and resolutions. Artefacts are referenced by URL and hash. Rendered views are derived and are not committed.

### 5.2 Lab records

Each version keeps three links to its lab record:

1. **A copy** of `lab.jsonl` in the registry, which keeps the hash chain verifiable whatever happens elsewhere.
2. **The author's repository URL pinned to a commit hash**, shown as the primary lab-notes link. Tags are recommended to authors but not relied on, since tags can be moved. Any public git host is accepted, and the link is optional.
3. **A Software Heritage identifier (SWHID).** At publication the portal sends save requests for the registry and for every repository on GitHub, GitLab or Codeberg that the version's artefacts link to; the archived snapshot, with its full history, survives deletion of the repository. Archiving happens later on Software Heritage's side, so v1 sends the requests and logs their answers; recording each SWHID in `versions.json` is left for later.

**Reading a lab record** (decided 20 November 2026, the maintainer: a study's record of 9.3 MB, nearly all result events, could be read neither on its repository's host nor by assistants). A log is for checking; people and models read its **reading view** (lab record v0.23 §11), which the claimset package makes from the log alone. When the portal writes a version's static files it makes, for a lab paper, the record's reading view and the **trail** of each claim exported from it (the trail of its `hypothesis.lab_event`, or of its `estimate.lab_plan` for a planned estimate: what was asked, planned, approved, run, checked and decided for it, in order), from the registry's copy of the log, or else from the author's log at its commit-pinned URL, fetched once (at most 50 MB; `PORTAL_LAB_FETCH=0` turns fetching off; a log that cannot be fetched or read gives no view, and the page links the log as before). Views are made again when the claimset package changes, and a fetch that fails is not tried again until then. A record's results are never listed there, only counted by run with the file that holds them (lab record v0.23 §5.10). The paper's page shows the record in a panel row *Lab record*: the readable record, the log, its summary (and, for the registry's copy, that its hash chain was verified), and one link to the paper's artefacts, the record view's list of them, which says where each is kept (a paper without a lab record and with artefacts has a row *Artefacts* with that link alone); the line under the byline says only that the paper was made with claimset-lab. A claim's page links its trail. Rows of the record that were written by contributors (lab record v0.23 §3.7) carry their ORCID iD in their IDs; the paper's header lists, in a fold *Contributions*, each contributor's CRediT roles as the claimset gives them, which export draws from the events each wrote.

### 5.3 Publication

The portal keeps a clone of the registry whose `main` follows GitHub. For a confirmed submission it writes the version on the branch `publish/<name>-v<n>`, pushes it as the GitHub App (the installation token goes to git in an HTTP header, never in a URL or command line), and opens the pull request. Each round of the worker then looks at the open pull requests: still checking, it waits; checks failed, it closes the pull request; checks passed, it squash-merges (only if the head is still the commit it pushed), tags the merge commit and updates its clone.

On merge: the static files are generated (§7), the version is indexed for search, the Software Heritage requests are sent, and the version becomes current. A new version moves the previous one to the history; every version stays retrievable.

### 5.4 Classification

The platform assigns each version the OpenAlex subfield and 1–3 topics (claimset spec §3.1, PLT-24), in v1. A separate classifier service runs OpenAlex's open title-and-abstract topic model (Apache-2.0, about 0.2B parameters, CPU) on the claimset's title and principal claims, with its keywords as a hint: a claimset has no abstract, and its principal claims serve as one. Model labels are matched to OpenAlex topics by ID (label n is topic T(10000+n); OpenAlex has renamed most topics since the model was trained, so names do not match), and each topic gives its subfield. A label whose topic OpenAlex has since retired (5 of about 4,500 in November 2026) is skipped; more than 1% retired fails the build. The image is built with one pinned commit of the model and the topic list fetched from OpenAlex at build time; the build fails if any label matches no topic. Fetching the topic list needs an OpenAlex API key (a free key; OpenAlex requires keys since February 2026), given to the build as a secret and kept out of the image. Each version records which classifier assigned its classification (`validation.json`). The model is not OpenAlex's full production classifier, which also uses journal and citation features, so a paper's labels can differ from those OpenAlex gives it.

## 6. Checks and screening

| Check | When | Cost |
|---|---|---|
| Package limits, validator, deterministic screening | Synchronously, on every submission | CPU only |
| `portal check` on the registry PR: only one new version folder added and nothing changed or deleted (append-only); identifier, folder and version consistent (next version, `previous_version`); validator in published-file mode; deterministic screening; lab record hash chain (lab record §6) | On the registry PR, by the registry's GitHub Actions, which install the current portal and the newest claimset | CPU only |
| LLM screening | On the registry PR, so only after consent | Built, but v1 launches without it (decided 2026-11-09): deterministic screening only. A small model, on the order of cents per claimset, when switched on |

**Safe-ingest screening (PLT-18).** Every free-text field is screened for content addressed to reading models, since EntryLib exists to place submitted text in other models' contexts.

- Deterministic rules (`screening-1`, codes SI1–SI4): invisible and direction-changing Unicode (zero-width joiners, which ordinary scripts need, are allowed); text addressed to a reading model (role markers, "ignore previous instructions" and the like); long encoded runs; links in claim statements. They add to the `claimset` validator's own narrower check (error `safe-ingest`). Homoglyph runs are not yet checked.
- LLM classifier (off at launch): the fields are given to a small model as data, with a public prompt, which reports any instruction, persuasion aimed at models, or non-research content.

A failure blocks publication and is reported to the submitter. Screening rules and the prompt are public and versioned, and each published version records the screening version that passed it.

Checks are event-driven. Batch APIs (roughly half price, results within a day) are an option if volume grows.

### 7.2 Search API

- `GET /api/search/claims?q=…` with filters on closed vocabularies: claim type, role, novelty label, planning, support kind, assumption check, licence (PLT-72, partly), and on the guarantor's ORCID iD (`guarantor`).
- `GET /api/search/papers?q=…`, with `licence` and `guarantor`. With `guarantor` and no `q`, it lists that guarantor's claimsets, newest first, so an author finds the identifier of a claimset to correct.
- Ranking at launch is Postgres full-text search: words reduced to their stems and matched against weighted text. For a claim: its statement first, then the terms of the definitions it cites and its scope, then the paper's title and keywords. For a paper: its title first, then its keywords and principal claims, then all its claims and definitions. Only current versions are searched. A claim matches on all its weighted text and is ranked by its statement (a claim whose statement matches comes before one that matches only through its definitions or paper): ranking reads each match's text, and the statement's is a tenth the size. The current versions' claims have their own index (`is_current`, migration 0016), the page of results is chosen before the papers' files are read, and a search has 32 MB of working memory, so that the index stays exact for words that match many claims. On a copy of 10,000 papers (715,000 claims) a claim search took 35 to 220 ms, a paper search 30 to 85 ms.
- Embeddings (vector similarity over each claim's statement and scope, combined with full text) and `GET /api/related/{id}` come after launch, when there are enough claimsets for meaning to matter more than words (PLT-73). They need no change to the format or to the API's results; pgvector is already in the database.
- Every result carries the version, its status and notices, and its validator warnings (PLT-13, PLT-74 in part).

### 7.3 MCP server

Served at `/mcp` from the same app with the official MCP Python SDK (PLT-71, PLT-11): the Streamable HTTP transport, stateless, answering in JSON, with no sign-in. Tools: `search_papers`, `search_claims`, `get_paper` (reading view or JSON, a version or the current one), `get_claim` (the claim bundle), `guide` (a skill of the claimset package by name, the specification or one of its sections, or EntryLib's good practice for planning a study, https://github.com/entrylib/study-planning: the list, one guide or one entry, from the copy the installed claimset carries, or the repository's address when it is too old to carry one), `upload_url` (§4.4), `validate`, `score` (§7.6), `submit` (the claimset JSON, with its text files or its package attached at consent; a package by `upload_id` or `package_url`), `submission_status`. Each calls the same code as the HTTP API, with the same limits. `related` comes with embeddings (§7.2). Tool results are data: their descriptions say so, as `/llms.txt` does. Answers are sized for an assistant's context: a claim search result carries the validator's warnings about that claim and a count of its paper's (`paper_warnings`), a paper card only the count (validate its `url` for the list); JSON is sent compact; and `get_paper` takes `part`, "overview" (the reading view's header and its sections with their sizes) or one section by name, since a whole reading view can run to tens of thousands of tokens. The score report names the score Support (the rubric's `report(name=…)`, through `claimset score`'s `describe`, each when the installed version takes it).

### 7.5 Retraction and removal

Decided 9 November 2026 (§15 Q5; portal issue #47). The form is at `/removal`, rendered by the app.

- **The guarantor** signs in with ORCID (the same callback as consent); if the iD is a guarantor of the current version, the request is applied at once. **Anyone else** gives an email address and their grounds; EntryLib reviews (`portal requests`, `portal decide <id> apply|decline`), and the notice then names EntryLib. The email and grounds are deleted when the request closes; a guarantor's request never confirmed is deleted after a day.
- **Reasons** come from a list ending with Other, which needs the requester's own words. Those words are screened (§6), shown as text only, and limited in length.
- **Retract:** the claimset stays, with `status: retracted` and a `status_notice` saying who, when and why, assigned by the platform (claimset spec §9) on every version as served: pages, JSON, reading views, search and `versions.json`. The registry's files are unchanged.
- **Remove:** the claimset's pages, files, bundles, citations and packaged files no other claimset uses are deleted, and each of its addresses answers with the notice (HTML, JSON, text). It leaves search and the listings; its identifier is never given again.
- **Registry:** one commit adds or extends `<folder>/notices.json` and, for a removal, deletes the claimset's versions; history is not rewritten. In github mode it is a pull request that the registry's check (§6) accepts only when it appends exactly one valid notice and, for a removal, deletes every version file and nothing else. `reindex` rebuilds retractions and removals from these files.
- **Served:** what readers find is the claimset specification's (§9): a retracted claimset with `status: retracted` and its `status_notice`; a removed one as `{"id", "status": "removed", "notice"}`. The rest (who may act, the reasons, `notices.json`) is EntryLib's policy, kept here and not in the specifications.

`notices.json`, in the claimset's registry folder, next to its versions:

```json
{"id": "entrylib:2026.000123",
 "notices": [{"action": "retracted", "date": "2026-11-10", "reason_code": "error_in_results",
              "reason": "Error in the results", "statement": "Table 2 reports the training error, not the test error.",
              "issued_by": "A. Researcher (ORCID 0000-0002-1825-0097)",
              "by": {"name": "A. Researcher", "orcid": "0000-0002-1825-0097"}, "versions": [1, 2]}]}
```

- `action`: `retracted` or `removed`. `reason_code`: from the lists in `notices.py` (each ends with `other`); `reason`: its name; `statement`: the requester's own words, possibly empty (required with `other`).
- `issued_by`: who acted, as readers see it: the guarantor by name and ORCID iD, or `EntryLib` after review; `by`: the guarantor's name and iD, or `null`. `versions`: the versions the claimset had when the notice was added.
- Notices are only appended, one per commit. A retraction changes nothing else. A removal deletes every file of every version, so the folder keeps only `notices.json`, and no notice may follow it.

### 7.6 Scores

Scores follow EntryLib's scoring rubric (github.com/entrylib/rubric, `RUBRIC.md`), installed from PyPI (`entrylib-rubric`) and updated each time the app starts, as claimset is. The rubric never affects the rest of the portal: if it fails (on import, a function the portal calls is missing, an error while scoring or writing the report), the scores are left out ("–"), the log says `RUBRIC ERROR` with what failed, and publication, the registry, the index and the pages go on; the portal applies it and never sets costs of its own. In short: a **Support** score from 0 to 100 for every claim that is not an assumption, computed by rules from the published file, each lost point naming its problem and what would remove it; the paper's is the mean of its principal claims', shown with the lowest (rubric 0.3). The portal gives the rubric the current validator's warnings for the file (warning 17, numbers no recorded result holds; warning 46, a limitation that restates the declared competing interest), validating the published file again when it scores it, so the scores follow the current validator as they follow the current rubric. **Novelty** is the authors' label with a close-match check against the claims of claimsets published before this one (candidates found by the portal's full-text search, the match decided by the rubric).

- **Competing interests, beside the score:** the panel shows, right after the score, the competing interests and funding the authors declare (`paper.declarations`), under "Conflicts of interest": only what is declared (funding only when there is a funder; "None declared." or "Not declared." otherwise), a long statement cut at about 90 characters with "more" to open it whole. Research can be done well and still be read differently once readers know who did it and why; that is for readers to weigh, so it is shown, never scored.
- **On the page:** the panel shows the paper's Support large, coloured by band (80+, 60–79, under 60) but not named (the claims' counts by band follow), with one link under the number, "Why 76?", to how it was made (the Score section's explanation, in a pop-up); then the five parts as a list, each a dot beside its name with the points lost (no colour key: the points say it). A paper's parts are the average its principal claims lost in each, rounded and coloured by the rubric's thresholds for a claim, so they read as a claim's do; the panel adds no sums or explanations, which "Why 76?" gives. The rubric's group *support* is called **Evidence** on the site, since *Support* is the score's own name; novelty small and uncoloured, with "What is this?" opening a pop-up that explains it and lists the principal claims by the authors' label. A panel taller than the screen scrolls on its own where it stays beside the page (wide and tall screens); on phones and tablets it is part of the page, and a drag on it scrolls the page. Every claim shows its score and five dots (evidence, plan, checkable, context, open problems), each dot explained on hover; clicking the score or the dots opens the claim's explanation in a pop-up (`page.js`). The dots are a link, reached with the keyboard and named for a screen reader with each part and its loss ("C11, parts of the score: Evidence, nothing lost; Plan, −5; …"), so they work without hover. The section *Score* at the end of the page holds the paper's explanation, so it can be linked and read without the script. A score's pop-up ("Why 76?", a claim's score) has a button, "Copy the issues for your agent", that copies the issues it lists as one block for the authors' agent: the version and its address, then what to do (suggest, for each issue, what to change or add in the claimset and where, from the specification, the skills and the paper, never from memory; say so when the paper lacks what an issue asks for, and which issues are not worth fixing; rewrite nothing yet, and wait for the authors to decide which changes go into a new version), then the issues, each formula as its source (`$…$`). The text is on the page, so the copy happens within the click; `/p/<key>@v<n>.issues.txt` stays for every issue at once. The explanation says that scores are computed by rules from the file and may change as the rubric and reviews develop.
- **For programs:** `/p/<key>@v<n>.score.json` (and `/p/<key>.score.json` for the current version) holds the scores, their problems and the rubric version; `/p/<key>@v<n>.issues.txt` lists every issue that lowers a score, with what would fix it, for the authors' agent preparing the next version (linked from the panel and the section *Score*); the reading view ends with the scores in text. Lists of claimsets (home, all, search) show each paper's Support.
- **A leaner claimset:** before submitting, `/llms.txt` asks the authors' agent to have a different agent review the claimset for text a reader does not need, from the candidates and the brief of `claimset lean` (the package's submission skill, step 11a), and to show its flags to their human, who decides what goes. The portal checks nothing of it.
- **Before submitting:** the authors' agent may score a claimset before it is submitted, as it would be scored once published: `claimset score` on their own machine, or the MCP tool `score` for an agent without a terminal. Optional; the agent asks its human whether to score, and the human decides whether to submit as it is or amend first. The scoring is in one place: the rubric (`rubric.assess`, which adds the close-match check over the claims a caller supplies, and `rubric.report`, the plain-text report), on the file as the claimset package prepares it (`claimset.validate.with_verifiability`, the verifiability the platform sets at publication). `claimset score` searches EntryLib's public claim search for the close-match check only with `--novelty`; the MCP tool uses the portal's search, and keeps nothing. The portal scores published versions with the same functions.
- **Novelty labels:** shown in words: new, extends, replicates or refutes earlier work, and, for claimset v0.43's `synthesis` (a claim that states what the works it cites establish, as a review's findings do), "summarises earlier work" (`scores.LABELS`, `page.NOVELTY_WORDS`, the Read filter's `read.NOVELTY`).
- **Cited claims:** from rubric 0.5, a claim that cites a claim published here (`id_type: claimset`, `entrylib:2026.000014@v2#C3`) costs by that claim's score here: the portal hands the rubric the scores from the score files it has written (`p/<key>@v<n>.score.json`, the current version's for an ID without a version), through the claimset package (`claimset.score.published_scores`, from 0.42.7; with an older package they cost as any cited work). Claimsets are scored in the order of their identifiers, the order they were first published, so the files a claimset cites exist when it is scored; a citing claimset is scored again when its pages are rewritten (a rubric change, a new version, a reindex), not when the claimset it cites gets a new version. The MCP tool `score` reads the same files.
- **Not claimed** (revised 20 November 2026, the maintainer: the list read "Reworded, then proved again: H1 → C1, H2 → C2, H3 → C3, H23 → C3, …", lab IDs a reader cannot look up): the paper's planned proofs that give no claim of their own (claimset v0.44 §3.1.1, `exploration.not_claimed`) are shown one item per entry, in an unnumbered list: the entry's `statement` (what its verdict decided, in a few words, its maths as formulae), then a short tail, the verdict and the reason in plain words ("— proved, then reworded", "— not proved, then merged", "— tried by proof, inconclusive, then dropped", "— void plan, repeated" for `because: defective`; a formal verdict's *supported* is *proved*), then a small link *lab record* to the paper's lab record (its artefact of kind `lab_record`, at an http(s) address), whose tooltip alone gives the lab IDs ("H4 under PL1", then every ID taken out of the text); no link without such an artefact. A lab ID is never an item's text. An entry without `statement` (a file before the amendment) shows its `why` instead (revised 20 November 2026, the maintainer: the fallback phrase "A dropped hypothesis" said nothing, and the reason was hidden), cleaned of lab IDs on display only: a hypothesis of this paper (a claim's `hypothesis.lab_event`, compared without a revision suffix such as `.R2` and with or without a writer's prefix such as `AC2.`) becomes its claim's ID, linked ("Merged into C4"); another hypothesis becomes "another hypothesis" ("part (iii) of another hypothesis"), or, after the word *hypothesis*, nothing; every other lab ID (decisions, plans, runs, deviations, results, questions, terms and the record's other events, with their prefixes and revision suffixes) is taken out, with the spaces and punctuation it leaves ("by the supervisor's decision DC5" reads "by the supervisor's decision", "from the simulation PL2" "from the simulation"). The `why` is shown as written otherwise, its reason included, with nothing put before it; one longer than about 200 characters is cut at the first sentence end after that, with "…", and the whole cleaned text is the item's tooltip. Only an entry with neither `statement` nor `why` reads "An earlier wording of this claim", "A hypothesis merged into this claim" ("… into another" without `into`), "A dropped hypothesis" or "A void plan". An entry with `into` stands under the claim it went into, folded (a `<details>`: *Earlier wordings (2)*, *Merged hypotheses (1)*, or *Earlier wordings and merged hypotheses (3)*): in the paper view under that claim, before its *Record* fold; on the claim's own page under the claim; and on the record under the claim too, so that the record still holds every entry. Only the entries without `into` (dropped, or merged into a hypothesis that gives no claim) stay in the section *Not claimed* after Score (in the contents with the count of what it lists), whose line says that earlier wordings are shown under their claims. Absent when it would list nothing. The preview shows it too.
- **When they change:** pages are rewritten when the rubric version changes (it is part of the marker of §7.1), so scores follow the current rubric. Without the rubric installed the page shows "–".

### 7.7 Read

`/read` (the menu's Read) shows what EntryLib holds. Rendered by the app, without scripts, from the index (decided 20 November 2026, the maintainer: "For Read, don't change how it looks"): the tree's counts, the filters, the sorts and the pages come from columns the indexer keeps (each paper's domain, field, subfield, score and band; each claim's position, score and band, and whether it is listed; migration 0018), and only the files of the papers a page shows are read. Until then every visit read every paper's file, which does not scale past a few thousand papers. `read.page`, from the files, stays as the reference the index must match, page for page (tests/test_read.py):

- **A tree** of OpenAlex domains, fields and subfields (`data/fields.json`, `data/subfields.json`), only the parts that have claimsets, each with how many. A claimset is in the subfield of its classification.
- **For the part chosen** (or everything): its **claimsets** as cards by default, or its **principal claims**, or all claims (a switch). Each claim shows its Support, dots and novelty, and links to its claimset.
- **Filters:** claim type, novelty label, planned test, planned estimate or exploratory, Support band; **sort** by Support or newest; 50 a page. The search box stays at the top.
- **Search** is the same page: with a query (`/read?q=…`) it searches the whole library, claimsets or claims (the same two tabs, claimsets first), says how many it found, and links back to browsing by field; the tree and filters step aside while searching. `/search` redirects here.
- Scores come from the rubric over each current file, kept in memory per version and rubric version; when the library grows, the indexer should store them in the database instead.

### 7.8 Search engines and link previews

- **Google Scholar:** every claimset page carries the Highwire tags Scholar reads (`citation_title`, `citation_author` for the people a citation names, publication and online dates, publisher EntryLib, keywords, the page as abstract and full text, `citation_reference` for references with a DOI).
- **schema.org (JSON-LD):** a claimset is a `ScholarlyArticle` (authors with their ORCID iDs, dates, licence, identifier, subfield, keywords, references, the JSON file as associated media); the home page names the `Organization` and the `WebSite`. JSON-LD is data in the page, never run; "<" in it is escaped.
- **Link previews:** Open Graph and Twitter tags, with one card for the site (`/og-card.png`, 1200×630); a claimset's preview also gives its Support.
- **Areas** of the Read page have their own addresses, `/read/<domain>/<field>/<subfield>` by name, each with its own title, description and canonical address (filters never make a new canonical page), listed in the sitemap when they hold a claimset; `/read?area=` answers with a redirect.
- **Answer engines** (AI search and assistants) quote and cite passages, but index pages: every principal claim has its own page (§7.1), which begins with the claim and gives its statement as the page's description, listed in the sitemap with the claimset's date. People reach it from the claim's ID on the claimset page.
- **Citation:** the reading view, the reading view as a web page and every claim bundle's reading view end with how to cite them (the claimset, and a claim as `entrylib:2026.000001@v3#C4` with its page's address). The claimset page's citation can be copied with one click. **Its form** (decided 22 November 2026, the maintainer): APA, without bracketed descriptions: "Svetunkov, I. (2026). The title (Version 6). EntryLib. https://entrylib.org/p/2026.000003@v6", a claim as "… (2026). Claim C4. In The title (Version 6). EntryLib. <its page>". It names the people a citation names (the human authors, else the guarantor) without a role: the guarantor takes an author's responsibilities, which APA gives as why AI cannot be one. How it was made is the BibTeX `note` and the RIS `N1` ("Claimset, written with Claude Opus 5.5 and Claude Sonnet 5.5", or "Claimset converted from <source> with …", then the identifier): the models as the byline names them, each once, "and others" after two. The BibTeX entry is `@misc` with `version` and `howpublished = {EntryLib}`.
- **IndexNow:** when a version is published the portal tells IndexNow (Bing, Yandex and others) its addresses at once, if `PORTAL_INDEXNOW_KEY` is set; the key is served at `/indexnow.txt`. Best effort; the sitemap lists everything anyway.

## 8. Limits and spam controls

| Limit | Value (initial) |
|---|---|
| Consent window | 48 hours, then deletion |
| New claimsets | 2 per ORCID iD in any seven days, counted against every confirming guarantor (20 while the library is seeded) |
| New versions (corrections now, revisions from v2) | 3 per claimset in any day (10 while the library is seeded) |
| Pending submissions | 5 per address at once |
| Reads: search, submission status, every MCP request | 120 per minute per address |
| Validation and scoring (`/api/validate`, `/api/score`, MCP `validate` and `score`, and building a LaTeX draft, §4.6, counted together) | 30 per hour per address |
| Submissions (`/api/submissions`, MCP `submit`) | 20 per hour per address |
| Upload addresses (MCP `upload_url`, and each `PUT` to one) | 10 per hour per address |
| Submissions by URL (`/api/submissions/from-url`, MCP `submit` with `package_url`) | 10 per hour per address, and 2 downloads at once across everyone |
| Package size | rule 77: 200 files, 50 MB a file, 200 MB in all |

- The per-address limits are token buckets kept in the app's memory (`ratelimit.py`): the app is one process, and a restart only forgets them. A request over a limit gets 429 with `Retry-After`; a download refused because two are running gets 503. Cloudflare limits at the edge as well, but only the app knows what a request costs.
- The address is the client's, not Cloudflare's: Caddy takes it from `CF-Connecting-IP` on requests from Cloudflare's address ranges only, and passes the app that one address in `X-Forwarded-For`, so it cannot be forged by sending the header or by going around Cloudflare. The ranges are in the Caddyfile; they change rarely and are updated by hand.
- The limits on new claimsets and versions (`limits.py`, the one place that holds them) count what is published or confirmed in the window and what is waiting for confirmation. A submission that would go over is refused when it is made (429), and a confirmation that would go over (the limit lowered meanwhile) is refused too; both say, in plain words, what the limit is, how much of it is used, and from when it can go on. The values in force are set by `PORTAL_MAX_NEW_PER_WEEK` and `PORTAL_MAX_VERSIONS_PER_DAY`; the defaults are raised while EntryLib is seeded and return to 2 and 3 once others submit (#64). Every page that states them (For agents) takes them from `limits.py`, never writes them out.
- ORCID iDs found abusing the service can be suspended (PLT-94). Consent is needed before anything is published, so unconfirmed spam costs validation only.

## 9. Notices and legal removal

Published versions are never withdrawn. Problems are marked with notices attached to a version: correction, expression of concern, retraction notice (PLT-91), each with a reason code and statement. The content stays available.

The one exception is legal: personal data, infringing or unlawful content. Such content is hidden, leaving a tombstone with the hash, date and reason. The policy is published.

## 10. Security

- Secrets in environment variables, never in the repository. Dependabot on the portal repo.
- Database reachable only from the app.
- The portal acts on GitHub as the EntryLib GitHub App, installed on the registry only, with contents and pull requests write access. Its private key is a file given to the portal as a Docker secret; installation tokens last an hour.
- The validator runs with time and memory limits; zips are unpacked with the limits of §4.1.
- Submitted content is never rendered as HTML: the pages show it escaped. Packaged files are served in a sandbox, never run: images are shown, other files downloaded.
- No access log: readers' IP addresses are used in memory for the limits only (§8), and a submission's address is deleted when it closes.
- The registry's check runs on every pull request, but merges happen only through the App, and only for pull requests it opened. If the LLM screening is switched on, its API key must be given only to runs on the App's own branches, never to pull requests from forks.

## 11. Dependence on GitHub

| Role | On GitHub | If GitHub fails |
|---|---|---|
| Authors | Not needed. Lab repositories may be on any public git host, or none | Unaffected |
| Registry | Hosted on GitHub | Archived by Software Heritage at every publication; the portal keeps its own clone and continues serving. A live mirror on a second host is set up at launch (step 10) |
| Checks | Run as GitHub Actions on the registry PR, for free compute and public logs | The checks are one container image (`portal check`); the portal runs it itself and commits to its own clone until GitHub returns or another host takes over |
| Code | `entrylib/portal` | Mirrored like the registry |

GitHub is the place where the record is published and the checks are logged, not something the platform cannot run without.

## 13. Hosting

One DigitalOcean Droplet in the London region with at least 4 GB RAM, set up by `deploy/cloud-init.yaml` and `deploy/server-setup.sh` and started by `deploy/launch.sh` (`docs/deploy.md`), running Docker Compose: the app, PostgreSQL with pgvector, and Caddy for HTTPS and static files. DigitalOcean's daily Droplet backups (crash-consistent disk images of everything on the Droplet: database, packaged files, pending submissions; volumes are not included, so nothing is kept on one). The published record is also the registry on GitHub, from which `reindex` rebuilds the database. DigitalOcean Spaces may later store packaged files. Cloudflare's free tier in front for DDoS protection and edge rate limits. DigitalOcean's managed PostgreSQL supports pgvector, so the database can move there later without code changes.

**Previews** (decided 22 November 2026, the maintainer: a change to the pages is to be clicked through before it reaches entrylib.org; and it is never run automatically). A workflow run by hand on a branch (`.github/workflows/preview.yml`) rebuilds the static pages with the branch's code from a sample of the published registry (`.github/preview-papers.txt`, the identifiers given when it is run, or all of it while it is small: a full rebuild of a large registry would take days and exceed what Cloudflare Pages takes) and uploads them to Cloudflare Pages, at `https://<branch>.entrylib-preview.pages.dev`, and says so in a comment on the branch's pull request. Only the static pages are there: search, submitting, consent and the MCP server need the app, and the server's rules on what a program is given at a page's address (§7.1) are Caddy's, so neither works in a preview; a link to a paper outside the sample finds no page. A preview is kept out of search engines (`robots.txt` and `X-Robots-Tag: noindex`) and touches neither the Droplet nor entrylib.org.

## 15. Open questions

1. **Domain.** Settled: entrylib.org. The production ORCID client will use the redirect URI https://entrylib.org/consent/callback.
2. **Paid accounts.** Publishing stays free. Candidates: higher read quotas on the API and MCP; higher submission quotas for verified organisations; private pre-submission checks, including a preview of the v2 reviewer's comments; bulk export.
3. **Several guarantors.** Whether 48 hours is enough when guarantors are in different time zones, or whether the window restarts when the first confirms.
4. **ORCID works.** Writing works to ORCID records needs ORCID membership. Until v3 brings DOIs and DataCite auto-update, guarantors add claimsets to their records by hand; the consent page says how.
5. **Legal removal policy:** who decides, the response time, and the tombstone format.
6. **Embedding model:** settled for launch: none; search is full text (§7.2). Which model, and when to re-embed if it changes, is decided when embeddings are added.
7. **Related work.** A head-to-head comparison with Knows (knows.academy), aiXiv and paper.json before any funding application.
